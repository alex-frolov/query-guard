*[English version](README.md)*

Расширение PHPUnit, которое смотрит на запросы, выполняемые из тестов, и находит
в них проблемы производительности, в первую очередь "N+1".

Поставили, добавили шесть строк в `phpunit.xml`, прогнали тесты как обычно. Никаких
"ассертов" в тестах, никакой отдельной команды, никаких правок кода.

> **Статус: 0.1.0 — первый публичный релиз.** Всё описанное ниже работает и покрыто
> тестами, которые гоняются на PHPUnit 10.5–13, Doctrine ORM 2–3, DBAL 3–4, MySQL и
> PostgreSQL. API может ещё поменяться до 1.0 — что уже переехало, написано в
> [UPGRADING.md](UPGRADING.md).

## Как это выглядит

```
query-guard
  тестов с трассой: 404, запросов: 25736 (в setUp: 0)

  находок: 207

  * [error] n-plus-one — App\Tests\Controller\TimesheetControllerTest::testExportAction
    App\Entity\Timesheet::$tags — ленивая загрузка связи, 10 запросов
    src/Entity/Timesheet.php:418

  * [warning] n-plus-one — App\Tests\Controller\TimesheetControllerTest::testSaveRates
    50 одинаковых по форме запросов из одного места, значения разные: SELECT r0_.id AS id_0, ...
    src/Repository/TimesheetRepository.php:810
```

Обе находки из настоящего проекта с прогона query-guard по "контроллерным" тестам
[Kimai](https://github.com/kimai/kimai). 207 срабатываний в 21 месте кода, включая три запроса ставок на каждый таймшит при каждом flush.

## Почему не статический анализ

**N+1 это не свойство запроса. Это свойство последовательности запросов.**

Это не рассуждение, а измерение. На MySQL, где разбор планов работает полностью, план
каждого отдельного запроса в учебном N+1 **безупречен**: `access_type: const`,
`key: PRIMARY`, одна строка, ноль замечаний. Проблема в том, что их пятьдесят. Ни один
`EXPLAIN` это не покажет.

Не скажет и анализатор по AST, ленивая загрузка случается при обращении к свойству,
динамические билдеры собираются в рантайме, и ни того ни другого в исходниках не видно.

| Инструмент | Зона | Пересечение с query-guard                                           |
|---|---|---------------------------------------------------------------------|
| [phpstan-dba](https://github.com/staabm/phpstan-dba) | **Статический SQL**: типы результата, синтаксис, плейсхолдеры, выводимые строки запросов | Нет. Он читает код, мы смотрим живой прогон. Стоит использовать оба |
| [phpstan-doctrine](https://github.com/phpstan/phpstan-doctrine) | Корректность DQL без базы | Нет                                                                 |
| [phpunit-query-count-assertions](https://github.com/mattiasgeniar/phpunit-query-count-assertions) | Счётчики запросов, дубли, EXPLAIN — через трейт и ручные ассерты | Ближайший аналог, см. ниже                                          |
| **query-guard** | **Рантайм-трасса**: что реально выполнилось, в каком порядке и откуда | —                                                                   |

### О ближайшем аналоге

Проверено на живых проектах, а не вычитано из README:

- дубли он ищет по совпадению SQL **и байндов**, поэтому настоящий N+1 — где значения
  по определению разные — даёт **ноль** дублей и зелёный тест;
- детект ленивой загрузки требует Laravel; на Doctrine `assertNoLazyLoading()` возвращает
  зелёное, ничего не проверив;
- тайминги на Doctrine недоступны (переиспользуется штатный логирующий middleware,
  который пишет запрос **до** выполнения), поэтому `assertMaxQueryTime(0.001)` проходит
  на шести реальных запросах;
- на PostgreSQL анализ планов молча выключается и рапортует зелёным при нуле
  проанализированных запросов.

query-guard пишет собственный DBAL-middleware (поэтому тайминги есть), считает "фингерпринт"
SQL с вырезанными значениями (поэтому N+1 виден) и говорит вслух, когда правило не может
судить, вместо того чтобы показать зелёное.

## Установка

```bash
composer require --dev alex-frolov/query-guard
```

```xml
<!-- phpunit.xml -->
<extensions>
    <bootstrap class="QueryGuard\Extension">
        <parameter name="mode" value="report"/>
    </bootstrap>
</extensions>
```

А дальше адаптер под вашу ORM, одна строка для Doctrine, ничего для Eloquent.

### Doctrine

Middleware должен быть прописан в конфигурации соединения **до** того, как соединение создано,
поэтому расширение не может поставить его автоматом:

```yaml
# config/services_test.yaml
services:
  QueryGuard\Adapter\Doctrine\Middleware:
    tags: ['doctrine.middleware']
```

Работает с Doctrine ORM 2 и 3, DBAL 3 и 4.

### Eloquent

Делать ничего не надо: Laravel сам находит `QueryGuardServiceProvider`.
Провайдер подписывается на диспетчер событий, поэтому видны все соединения,
в том числе созданные позже, и запросы из `setUp()`.

### Что-нибудь другое

Коллектор — это точка стыка. Давайте ему данные из декоратора PDO, другой ORM, или откуда угодно:

```php
use QueryGuard\Query\QueryEvent;
use QueryGuard\QueryGuard;

QueryGuard::collector()->record(new QueryEvent(
    sql: 'SELECT * FROM users WHERE id = ?',
    params: [42],
    durationMs: 0.4,
    stack: debug_backtrace(DEBUG_BACKTRACE_IGNORE_ARGS),
));
```

Вне прогона из под PHPUnit коллектор это заглушка, такой код ничего не делает и ничего не стоит.

Если место запроса уже известно, передайте `callsite:` вместо `stack:` — тогда обход стека
не нужен вовсе. Именно так работают оба встроенных адаптера.

## Правила

### Первый этап — работает сразу, reference-база не нужна

| Правило | Что значит | По умолчанию |
|---|---|---|
| `n-plus-one` | Одна форма запроса, одно место в коде, разные значения | включено, порог 3 |
| `duplicate-query` | Тот же запрос с теми же значениями, повторно | включено, порог 5 |
| `query-in-loop` | Много запросов **разных** форм из одного места | включено, порог 5 |
| `no-limit` | `SELECT` без `LIMIT` по таблице, помеченной как крупная | молчит без `large-tables` |
| `select-star` | `SELECT *` | выключено |
| `query-count` | Бюджет запросов на тест | молчит без `max-queries` |

Три правила молчат, пока их не настроят, это сделано специально. 
`select-star` сработал бы на каждом запросе Eloquent (там это режим по умолчанию), 
«крупную таблицу» на фикстурной базе в три строки определить нечем, 
а количество запросов - архитектура проекта, а не константа.

`n-plus-one` смотрит только на чтения, требует, чтобы значения повторов различались,
и не считает пакетные выборки (`IN (?, ?, ?)`) - это **лекарство** от N+1, а не болезнь.

### Второй этап — правила плана, нужна база с настоящими данными

Включается `tier2="true"`. Выполняет `EXPLAIN` по разу на уникальную форму запроса,
на том же соединении и в той же транзакции.

**Несколько соединений обрабатываются по отдельности.** Каждое объясняется само по себе,
своим драйвером платформы — запрос, выполнявшийся на аналитической базе, никогда не будет
объяснён на основной. Соединение на неподдерживаемой платформе называется в сводке и
пропускается; остальные продолжают работать.

| Правило | MySQL / MariaDB | PostgreSQL |
|---|---|---|
| `no-possible-index` | ✅ | — платформа не сообщает индексы-кандидаты |
| `table-scan` | ✅ | ✅ |
| `filesort` | ✅ | ✅ |
| `temporary-table` | ✅ | — аналога, о котором стоит предупреждать, нет |

Где правило не работает, сводка **говорит об этом**. 
Зелёный отчёт и «мы не смотрели» не должны выглядеть одинаково.

**Второму этапу нужен объём.** Правила плана молчат, пока в таблице меньше `min-rows` строк
(по умолчанию 1000): на маленькой таблице врёт сама оценка оптимизатора, мы видели,
как конкурент выдал `error: Full table scan` на таблице из пяти строк. 
Одно исключение - `no-possible-index` отсутствие индекса это факт схемы, верный и на пустой таблице.

## Когда query-guard молчит

Инструмент, показывающий зелёное там, где он не смотрел, хуже, чем никакого. Всё из
списка ниже попадает в сводку как уведомление — кроме трёх последних строк, которые
молчат осознанно:

| Ситуация | Что вы увидите |
|---|---|
| ORM в проекте не найден | `neither Doctrine nor Eloquent was found` |
| ORM найден, перехват не встал | назван адаптер и конкретное действие для починки |
| Перехват встал, но за весь прогон ни одного запроса | `not "all clear", it is "nothing to look at"` |
| Запросы вне границ теста (bootstrap, дата-провайдеры) | посчитаны, счётчик в сводке |
| Значение параметра, которое не удалось прочитать | параметр, значение и что взято вместо него |
| `tier2` включён, соединение так и не появилось | `no plans were looked at` |
| `tier2` на неподдерживаемой платформе | платформа названа, поддерживаемые перечислены |
| `no-possible-index` на PostgreSQL | правило говорит, что судить не может, а не что всё хорошо |
| `temporary-table` на PostgreSQL | то же |
| **`--no-output`** | ничего: расширение вообще не загружается |
| **Таблица меньше `min-rows`** | ничего: правила плана намеренно не судят маленькие таблицы |
| Слушатель Eloquent достал только одно соединение | сводка говорит какое и как покрыть остальные |
| Два соединения Doctrine с одинаковым именем базы | оба сохранены; второе переименовано, и о переименовании сказано |
| Записи baseline, которые ничего не заглушили | посчитаны, с оговоркой, что это значит после отфильтрованного прогона |
| **`#[IgnoreRule]` / запись в baseline** | счётчик baseline показывается, точечное исключение — нет |

Ещё два факта:

- **Второй этап не работает на Eloquent.** `QueryExecuted` не даёт доступа к соединению,
  на котором можно выполнить `EXPLAIN` внутри той же транзакции, а подставлять тихо
  нечего. Первый этап работает полностью.
- **Запросы из `setUp()` не анализируются.** Они считаются и показываются отдельно
  (`in setUp: N`). На этом решении держится вся история с ложными срабатываниями:
  фабрика, создающая 50 строк в цикле, — это 50 одинаковых INSERT из одного места. По той
  же причине бюджет `max-queries` считается по телу теста.
- **Под параллельным раннером каждый воркер — отдельный прогон.** ParaTest поднимает
  процесс на воркер, и увидеть их вместе query-guard не может: каждый печатает свою
  сводку, ведёт свои счётчики и в режиме `strict` валит свой процесс. Находки при этом
  верны — трейс никогда не пересекает воркеров, — но «findings: 3», напечатанное четыре
  раза, это четыре частичных отчёта, а не двенадцать находок. Направьте `report-json` в
  путь на воркер (`var/query-guard-$TEST_TOKEN.json`) и сливайте файлы, либо гоняйте
  query-guard отдельной последовательной задачей.

## Чего это стоит

То, что стоит знать до включения в CI, и не на глаз, а по замеру:

| | Цена |
|---|---|
| Вне прогона PHPUnit | ничего. Коллектор — null-объект, стек не снимается |
| Между тестами, в `setUp()` | запрос записывается, правила не запускаются |
| На запрос внутри трейса | один `debug_backtrace` (200 кадров) и одно разрешение callsite — **~0.006 мс, то есть ~0.15 с на 25 000 запросов** |
| Память на запрос внутри трейса | SQL, значения и один callsite — **~0.5 МБ на 1000 запросов**, освобождается по концу теста |
| Второй этап | один `EXPLAIN` на *уникальную форму запроса* за прогон, а не на запрос; на PostgreSQL плюс один запрос размера на таблицу |
| Конец прогона | правила отрабатывают по трейсу сразу за тестом, сводка печатается один раз |

Стек снимается только пока идёт трассировка теста, и хранится из него только
разрешённый callsite: 200 сырых кадров на запрос стоили около 106 МБ на 1000 запросов и
были единственным способом, которым этот инструмент мог навредить сюите.

Настоящая цена — у второго этапа: он ходит в базу. Собственные запросы инструмента из
трейса исключены, так что свой трафик он никогда не считает.

## Baseline

Прогоните query-guard на существующем проекте и получите сотни находок. Для этого и нужен baseline:

```bash
QUERY_GUARD_GENERATE_BASELINE=1 vendor/bin/phpunit
```

```xml
<parameter name="baseline" value="query-guard-baseline.json"/>
```

Известное молчит, новое видно. Файл коммитится в репозиторий.

Ключ находки — `правило|файл|фингерпринт`, намеренно **без** номера строки и **без** имени
теста, и то и другое съезжает время от времени и, в таком случае, указывает не туда в baseline. 
Пути внутри относительные, поэтому файл переживает переезд в CI.

Сводка всегда сообщает, сколько находок baseline заглушил.

### Что лежит в файле

```json
{
    "generated-at": "2026-09-03T10:12:00+00:00",
    "comment": "query-guard baseline: the findings listed here do not fail the run...",
    "findings": {
        "n-plus-one|src/Entity/Timesheet.php|select t0.id from tags t0 where t0.id = ?": {
            "rule": "n-plus-one",
            "place": "src/Entity/Timesheet.php:418",
            "sample": "App\\Entity\\Timesheet::$tags — lazy-loaded association, 10 queries"
        }
    }
}
```

Заглушает находку **ключ**; всё, что под ним, лежит там, чтобы файл можно было прочитать
в пул-реквесте. `place` несёт номер строки, который ключ намеренно не включает, а
`sample` — сообщение таким, каким оно было в момент записи; ни то, ни другое не
сопоставляется и не обновляется. Чтобы снова начать падать на находке, удалите ключ
руками; правка `place` или `sample` не меняет ничего.

### Записи, пережившие свои находки

Находку починили — запись в baseline осталась и глушит то, чего больше нет, а со временем
и свежую регрессию, попавшую в то же правило в том же файле. Поэтому прогон сообщает,
сколько записей не совпало ни с чем:

```
  ! 4 baseline entries silenced nothing in this run.
    After a full-suite run they are obsolete: regenerate with QUERY_GUARD_GENERATE_BASELINE=1 to drop them.
    After a filtered run it only means those tests did not execute.
```

Различие здесь и есть весь смысл формулировки. `--filter`, `--exclude-group`, шардированная
задача в CI — любое из этого оставляет записи несовпавшими, и ничего при этом не протухло.
Перегенерировать — только из полного прогона, либо не перегенерировать вовсе.

## Машиночитаемый отчёт

Сводка выше написана, чтобы её читал человек, а значит, её формулировки будут меняться.
Всему автоматическому стоит читать вот это:

```xml
<parameter name="report-json" value="var/query-guard.json"/>
```

```json
{
    "generated-at": "2026-09-03T10:12:00+00:00",
    "mode": "strict",
    "fail-on": "warning",
    "failing": true,
    "summary": {"tests": 404, "queries": 25736, "fixture-queries": 0, "suppressed": 0, "findings": 207},
    "notices": ["tier 2: 118 plans parsed, 0 failed."],
    "findings": [
        {
            "rule": "n-plus-one",
            "severity": "error",
            "test": "App\\Tests\\Controller\\TimesheetControllerTest::testExportAction",
            "class": "App\\Tests\\Controller\\TimesheetControllerTest",
            "method": "testExportAction",
            "message": "App\\Entity\\Timesheet::$tags — lazy-loaded association, 10 queries",
            "file": "src/Entity/Timesheet.php",
            "line": 418,
            "count": 10,
            "signature": "n-plus-one|src/Entity/Timesheet.php|select t0.id from tags t0 where t0.id = ?"
        }
    ]
}
```

Пути относительны рабочей директории, так что файл переживает переезд в CI. `failing`
отвечает на единственный вопрос, который обычно есть у CI-скрипта, — упадёт ли этот
прогон, — не заставляя его переизобретать сравнение с `fail-on`. Консольную сводку файл
не заменяет никогда: прогон, который пишет отчёт и ничего не печатает, — это прогон, чьих
находок никто не увидит.

## Точечные исключения

```php
use QueryGuard\Attribute\AllowQueries;
use QueryGuard\Attribute\IgnoreRule;

#[AllowQueries(50)]
#[IgnoreRule('n-plus-one')]
public function testImportsLargeFile(): void
```

Оба атрибута работают и на классе, и на методе. `#[IgnoreRule]` повторяемый, и метод
добавляет к тому, что уже игнорирует класс; `#[AllowQueries]` на методе заменяет бюджет
класса, а не складывается с ним.

Если callsite приземляется внутрь фреймворка, который проект просто вендорит, и никакой
`#[IgnoreRule]` не поможет — потому что правило право, а файл не ваш, — добавьте пакет в
`skip-paths`:

```xml
<parameter name="skip-paths" value="vendor/api-platform,vendor/sonata-project"/>
```

Это фрагменты путей, а не регулярные выражения, и они добавляются ко встроенному списку
(PHPUnit, Doctrine, Symfony, Laravel, Illuminate, Composer), а не заменяют его. Находка
показывает на первый кадр вне всех перечисленных путей.

## Параметры

| Параметр | Значение | По умолчанию |
|---|---|---|
| `mode` | `report` — печатать сводку; `strict` — валить прогон | `report` |
| `fail-on` | Минимальная строгость, на которой `strict` валит прогон: `error`, `warning`, `info` | `warning` |
| `baseline` | Путь к файлу baseline | не задан |
| `n-plus-one-threshold` | Со скольких повторов считать N+1 | `3` |
| `duplicate-threshold` | Со скольких повторов считать дублем | `5` |
| `query-in-loop-threshold` | Со скольких запросов из одного места | `5` |
| `max-queries` | Бюджет запросов на тело теста — `setUp()` считается отдельно и в бюджет не входит | не задан, правило молчит |
| `large-tables` | Таблицы для `no-limit`, через запятую; имя без схемы совпадает с таблицей в любой схеме, имя со схемой (`public.orders`) — только в ней | не задан, правило молчит |
| `select-star` | Включить `select-star` | `false` |
| `tier2` | Включить правила плана | `false` |
| `min-rows` | Размер таблицы, ниже которого правила плана не судят | `1000` |
| `skip-paths` | Фрагменты путей через запятую, на которые callsite никогда не показывает, — ваши собственные фреймворки, вдобавок ко встроенному списку | не задан |
| `report-json` | Куда писать машиночитаемый отчёт; сводка в консоль печатается в любом случае | не задан, ничего не пишется |

**`fail-on` читает шкалу строгости.** `[error]` — адаптер распознал ленивую загрузку и
назвал ассоциацию; `[warning]` — сработала только эвристика по форме запроса; `[info]` —
замечание о стиле. Печатается всегда всё найденное; `fail-on` решает лишь, из-за чего
`strict` готов уронить прогон. Значение по умолчанию `warning` намеренно оставляет
`info` в стороне: единственное `info`-правило — `select-star`, а `select *` для Eloquent
режим по умолчанию, и падение на нём покрасило бы весь Laravel-сьют в тот же момент, как
правило включили. Поставьте `fail-on="error"`, чтобы валиться только на доказанном, а не
на предположенном.

Значение, которое не удалось прочитать — `mode="strickt"`, `max-queries="много"` — даёт
предупреждение в сводке с именем параметра, самим значением и тем, что взято вместо него.
Тихого отката к умолчанию не бывает. Единственное, что поймать нельзя, — опечатка в
*имени* параметра: `ParameterCollection` в PHPUnit не даёт перечислить написанное.

Режим `strict` валит **прогон** (код возврата 1), а не отдельный тест: событийная система
PHPUnit не даёт расширению пометить тест упавшим. Если PHPUnit и так валит прогон по
своим причинам, его код возврата остаётся нетронутым — он точнее.

## Рецепты

### Поймать N+1 за пять минут

Без baseline, без strict, без второго этапа — навести на один тест и прочитать вывод.

**1. Поставьте расширение и подключите адаптер** (раздел «Установка» выше). Умолчаний
достаточно: `n-plus-one`, `duplicate-query` и `query-in-loop` включены сразу, шумные
правила выключены.

**2. Прогоните один подозрительный тест:**

```bash
vendor/bin/phpunit --filter testExportAction
```

**3. Прочитайте сводку.** Находка называет правило, тест, диагноз и строку:

```
  * [error] n-plus-one — App\Tests\Controller\TimesheetControllerTest::testExportAction
    App\Entity\Timesheet::$tags — lazy-loaded association, 10 queries
    src/Entity/Timesheet.php:418
```

`[error]` значит, что адаптер распознал ленивую загрузку и гадать больше не о чем.
`[warning]` значит, что сработала только эвристика формы — тот же запрос, то же место,
разные значения: посмотреть стоит, но это не приговор.

**Ничего не нашлось?** Прежде чем решить, что проблемы нет, посмотрите на шапку сводки:
`tests traced: 1, queries: 0` означает, что перехват не встал, а уведомление ниже скажет,
что чинить. См. [Когда query-guard молчит](#когда-query-guard-молчит).

Когда захотите держать под этим всю сюиту — читайте дальше.

### Как читать три правила о группировке

`n-plus-one`, `duplicate-query` и `query-in-loop` все говорят «из одного места ушло много
запросов» — и это три разных диагноза с тремя разными способами лечения. Различает их то,
как выглядит трейс:

| Что в трейсе | Правило | Что это значит | Чем лечится |
|---|---|---|---|
| Одна форма, одно место, **значения разные** | `n-plus-one` | По строке за раз — из цикла или из ленивой ассоциации | Забрать всё одним запросом: `JOIN`, `IN (...)`, eager loading |
| Одна форма, одно место, **значения совпадают** | `duplicate-query` | Первый ответ выбросили | Сохранить результат или закешировать. С самим запросом всё в порядке |
| **Разные формы**, одно место | `query-in-loop` | На каждой итерации своя работа — сущность, потом её настройки, потом владелец | Обычно одна перестройка выше по коду, а не три починки |

Два правила никогда не срабатывают на одних и тех же запросах: `n-plus-one` требует, чтобы
значения различались, `duplicate-query` — чтобы совпадали, а `query-in-loop` отступает,
когда в группе одна форма. Если на одной строке кода висят все три, они описывают три
разных набора запросов, которые просто уходят из неё.

Строгость — вторая половина сообщения, и означает она уверенность, а не цену. `[error]` на
`n-plus-one` — это адаптер, распознавший ленивую инициализацию Doctrine и назвавший
ассоциацию: гадать больше не о чем. `[warning]` — только эвристика по форме.

### Что делать с найденным N+1

Находка даёт файл, строку и форму запроса. Чего она не может сказать — какой из трёх
способов чинить подходит, потому что это зависит от того, что код делает со строками.

**Doctrine — ленивая ассоциация в цикле.** Обычный случай, и как раз тот, что приходит
как `[error]` с названной ассоциацией:

```php
// было: один запрос за таймшитами, дальше по одному на каждый — за тегами
foreach ($repository->findBy(['user' => $user]) as $timesheet) {
    $names[] = implode(', ', $timesheet->getTags()->map(fn (Tag $t) => $t->getName())->toArray());
}

// стало: ассоциация приезжает вместе с родителем, одним запросом
$timesheets = $repository->createQueryBuilder('t')
    ->addSelect('tags')          // без addSelect джойн фильтрует, но не гидрирует
    ->leftJoin('t.tags', 'tags')
    ->where('t.user = :user')->setParameter('user', $user)
    ->getQuery()->getResult();
```

Весь фокус в `addSelect`, и забыть его — самый частый способ «починить» так, чтобы ничего
не изменилось: один `leftJoin` оставляет коллекцию ленивой. Не тянитесь вместо этого к
`fetch: 'EAGER'` в маппинге — тогда за ассоциацию будет платить каждое чтение этой
сущности во всём приложении.

**Doctrine — много сущностей по id, не через ассоциацию:**

```php
// было: findOneBy в цикле
foreach ($ids as $id) { $orders[] = $repository->find($id); }

// стало: один запрос, проиндексированный для выборки
$orders = $repository->createQueryBuilder('o')
    ->where('o.id IN (:ids)')->setParameter('ids', $ids)
    ->indexBy('o', 'o.id')
    ->getQuery()->getResult();
```

`IN (?, ?, ?)` query-guard пропускает намеренно: пакетная выборка — это лекарство, и
правило не должно объявлять лекарство болезнью.

**Eloquent:**

```php
// было
foreach (Order::all() as $order) { $total += $order->items->sum('price'); }

// стало — жадная загрузка вместе с родительским запросом
foreach (Order::with('items')->get() as $order) { $total += $order->items->sum('price'); }

// или, когда коллекция уже есть
$orders->load('items');
```

**И проверьте.** Перезапустите тот же один тест и прочитайте сводку, а не считайте, что
починилось:

```bash
vendor/bin/phpunit --filter testExportAction
```

Находка исчезает, число запросов падает. Если число не упало — починка не сработала:
негидрирующий джойн или ленивая загрузка, которая переехала, а не ушла. Если на месте
`n-plus-one` появился `duplicate-query` — цикл теперь повторяет один и тот же запрос
вместо запроса на строку: почти всё, и осталось сохранить результат, а не менять запрос.

### Внедрение на легаси-проекте

Починить сотни старых тестов одним походом нельзя, и не нужно. Цель - провести черту,
всё существующее уходит в baseline, всё новое проверяется. 
Шаги - от установки до `strict`.

**1. Установите и включите все проверки.** Расширение и адаптер — как в разделе
«Установка» выше. Режим пока `report` — сначала измеряем масштаб бедствия, — а путь к
baseline прописываем сразу: шаг 5 запишет в него всё найденное:

```xml
<!-- phpunit.xml -->
<extensions>
    <bootstrap class="QueryGuard\Extension">
        <parameter name="mode" value="report"/>
        <parameter name="baseline" value="tests/query-guard-baseline.json"/>
        <parameter name="n-plus-one-threshold" value="3"/>
        <parameter name="duplicate-threshold" value="5"/>
        <parameter name="query-in-loop-threshold" value="5"/>
        <parameter name="max-queries" value="50"/>
        <parameter name="select-star" value="true"/>
        <parameter name="large-tables" value="users,orders"/>
    </bootstrap>
</extensions>
```

`max-queries` здесь — зонд, а не бюджет, с которым вы останетесь: см. шаги 3 и 4.

**2. Прогоните тесты и сохраните лог.** Находки и счётчики запросов пишутся в stdout:

```bash
vendor/bin/phpunit 2>&1 | tee query-guard.log
```

**3. Выберите настоящий `max-queries` по логу.** Печатаются только перерасходы, строкой
`N queries against a budget of M`, — то есть один прогон показывает тесты выше зонда и
ничего про остальные. Чтобы увидеть форму распределения, прогоните дважды: с низким
зондом (скажем, 20) и с высоким (скажем, 100). По двум прогонам у вас есть точный счётчик
каждого теста.

```bash
grep 'against a budget' query-guard.log
```

Рекомендации:

- глобальный бюджет — около 90–95-го перцентиля обычных бизнес-тестов; число, выбранное
  «с запасом», не защищает ничего;
- действительно тяжёлым тестам (массовый импорт, выгрузка, отчёты) — персональный
  `#[AllowQueries(N)]`, а не раздутый глобальный бюджет;
- легаси, которое нельзя трогать, оставьте baseline (шаг 5): находки `query-count`
  ключуются по тесту, так что новые тесты по бюджету всё равно проверяются.

**4. Впишите выбранный бюджет обратно в `phpunit.xml`** — зонд из шага 1 всё ещё там, а
шаг 5 вот-вот заморозит всё, что этот зонд даст:

```xml
<parameter name="max-queries" value="35"/>
```

Именно до генерации baseline, а не после. Baseline, снятый с зондом, зафиксирует находки
`query-count` не по тому порогу, и снижение бюджета потом будет выглядеть как волна
регрессий.

**5. Создайте baseline и закоммитьте его:**

```bash
QUERY_GUARD_GENERATE_BASELINE=1 vendor/bin/phpunit
```

Всё найденное попадёт в `tests/query-guard-baseline.json`; файл — в репозиторий.

> **Переменную ставьте на одну команду и никогда — в CI.** С ней прогон всегда зелёный и
> всегда переписывает baseline: тише способа насовсем выключить инструмент не бывает.
> Если переменная выставлена, а параметра `baseline` нет, сводка об этом скажет, и ничего
> записано не будет.

**6. Решите вопрос со вторым этапом — он нужен, только если тесты идут на базе с настоящими
объёмами.** Правилам плана нужны строки и статистика; на фикстурной базе в три строки
оценка оптимизатора врёт, и правила приносят больше вреда, чем пользы (см. раздел
«Второй этап» выше). Если тестовая база — копия продовой или сидируется масштабно, добавьте:

```xml
<parameter name="tier2" value="true"/>
```

и перегенерируйте baseline (шаг 5), чтобы зафиксировать и находки плана.

**7. Перепрогоните и проверьте:**

```bash
vendor/bin/phpunit 2>&1 | tee query-guard-after.log
```

В сводке должно быть `silenced by baseline: N` — и больше ничего. Всё, что всё же
появилось, — либо «плавающее» место в коде, либо регрессия между двумя прогонами;
baseline тут ни при чём.

**8. Переключите режим в `strict`:**

```xml
<parameter name="mode" value="strict"/>
```

С этого момента любая находка вне baseline валит прогон: новый N+1 в новом тесте,
съехавший callsite старого, перерасход бюджета у теста, которого не было, когда baseline
писался.

**Привычка, которую стоит завести вместе с инструментом:** готовьте тестовые данные в
`setUp()`, а не в теле теста. Трасса открывается после `setUp()`, поэтому INSERT'ы фабрик
туда не попадают; тот же цикл создания фикстур внутри тела теста — учебный false
positive по `n-plus-one`/`duplicate-query` на ваших же данных.

### Новый проект

Легаси нет, baseline не нужен: каждая находка — либо чинимый баг, либо исключение,
которое вы обосновываете письменно. Включаем всё, что работает с первого дня; на время
разбора оставляем `report`:

```xml
<!-- phpunit.xml -->
<extensions>
    <bootstrap class="QueryGuard\Extension">
        <parameter name="mode" value="report"/>
        <parameter name="n-plus-one-threshold" value="3"/>
        <parameter name="duplicate-threshold" value="5"/>
        <parameter name="query-in-loop-threshold" value="5"/>
        <parameter name="max-queries" value="30"/>
        <parameter name="select-star" value="true"/>
    </bootstrap>
</extensions>
```

Ещё два параметра стоит добавить, но каждый — только когда выполнено его условие: в
отрыве от проекта осмысленного значения у них нет.

```xml
<!-- ваши крупные таблицы, поимённо; без списка правило молчит. Имя без схемы
     совпадает с таблицей как бы её ни написал запрос — `orders`, `public.orders`,
     `"public"."orders"`. Напишите `public.orders`, чтобы иметь в виду именно эту схему -->
<parameter name="large-tables" value="users,orders"/>

<!-- только когда в тестовой базе настоящие объёмы: на фикстурной оценка оптимизатора
     врёт, и правила плана приносят больше вреда, чем пользы -->
<parameter name="tier2" value="true"/>
```

**1. Прогон и лог:**

```bash
vendor/bin/phpunit 2>&1 | tee query-guard.log
```

**2. Разберите каждую находку.** Вердиктов три:

- *истинное срабатывание* — чиним код, а не конфиг: eager-загрузка (`JOIN`/`IN`) вместо
  ленивой, один пакетный запрос вместо запроса на строку, недостающий индекс за
  `table-scan` или `no-possible-index`;
- *тест задуман тяжёлым* — массовый импорт, выгрузка отчёта: исключение на тест (шаг 3),
  а не поднятый глобальный бюджет;
- *ложное срабатывание* — правило оценило шаблон, сквозь который не видит: исключение на
  тест с комментарием, почему.

**3. Исключения — как ставить их правильно:**

```php
use QueryGuard\Attribute\AllowQueries;
use QueryGuard\Attribute\IgnoreRule;

// бюджет под реальную работу теста — фактическое число видно в логе
#[AllowQueries(120)]
public function testBulkImport(): void

// выключить ровно то правило, которое ошиблось; аргумент — id правила дословно
// из заголовка находки: [warning] n-plus-one — ...
#[IgnoreRule('n-plus-one')]
public function testLegacyPdfExport(): void

// атрибуты можно повесить на весь класс вместо повтора на каждом тесте
#[IgnoreRule('select-star')]
final class ReportQueryTest extends TestCase
```

`#[AllowQueries]` на методе перекрывает классовый; `#[IgnoreRule]` повторяется и
складывается с тем, что игнорирует класс. Исключения держим узкими: одно правило на один
метод лучше, чем три правила на весь класс. Исключение без комментария-причины — с этого
начинается гниль.

**4. Когда лог чист — режим `strict`:**

```xml
<parameter name="mode" value="strict"/>
```

На новом проекте baseline опционален: каждая находка свежая, чинить её дешевле, чем
копить. Вырастете — параметр `baseline` уже здесь.

### Запуск в CI

Отдельная задача расширению не нужна — оно едет вместе с тем сьютом, который вы и так
гоняете. Что добавляет CI, так это место, куда положить отчёт, и правило про baseline.

**1. Писать машиночитаемый отчёт и сохранять его:**

```yaml
- name: Tests
  run: vendor/bin/phpunit

- name: Keep the query-guard report
  if: always()          # падение по strict — как раз когда файл и нужен
  uses: actions/upload-artifact@v4
  with:
    name: query-guard
    path: var/query-guard.json
```

при `<parameter name="report-json" value="var/query-guard.json"/>` в `phpunit.xml`. Смысл
шага именно в `if: always()`: без него артефакт заливается только в тех прогонах, где он
никому не нужен.

**2. Никогда не ставьте `QUERY_GUARD_GENERATE_BASELINE` в CI.** С ним прогон всегда
проходит и всегда переписывает baseline. Это самый тихий способ выключить инструмент
навсегда — тише, чем удалить его, потому что задача остаётся зелёной, а файл продолжает
меняться. Перегенерация — локальная команда, а её результат — отревьюенный коммит.

**3. Ревьюйте diff baseline как код.** Пул-реквест, добавляющий записи, — это
пул-реквест, привозящий известные проблемы, и diff показывает какие именно:

```diff
+        "n-plus-one|src/Repository/OrderRepository.php|select t0.id from items t0 where t0.order_id = ?": {
+            "rule": "n-plus-one",
+            "place": "src/Repository/OrderRepository.php:88",
```

Иногда это правильное решение — дедлайн, уже запланированный рефакторинг. Ценность в том,
что решение было принято человеком с именем, а не правило тихо не сработало.

**4. Читайте счётчики, а не только код возврата.** `tests traced: 0` или `queries: 0` —
это зелёная сборка, которая ничего не проверила, и выглядит она ровно как чистая, пока
кто-нибудь не прочитает две цифры в начале сводки. В JSON они лежат под `summary`, и
проверять их проще.

### Проект с несколькими базами

Второй этап разбирается с соединениями по отдельности по построению: каждое объясняется
само по себе, через то соединение, которое выполнило запрос, и своим драйвером платформы.
От вас нужен в основном способ убедиться, что так и вышло.

**Какие соединения увидены.** Сводка называет каждое, которое пришлось пропустить, и
почему:

```
  ! the "analytics" connection runs on "clickhouse", which tier 2 does not support — its
    queries were not explained.
    Supported: MySQL/MariaDB and PostgreSQL. Other connections are unaffected.

  ! tier 2: 118 plans parsed, 0 failed.
```

`0 failed` рядом с правдоподобным числом планов — так выглядит работающий второй этап.
Большое число в `failed` обычно означает, что EXPLAIN отказывают, а не что план не
разобрали: права доступа или запрос, который платформа объяснять не станет.

**Соединения называются по имени базы.** Два соединения с одинаковым `dbname` — чаще
всего primary и реплика для чтения — различаются по хосту, порту и пользователю, и второе
попадает в сводку под именем с суффиксом:

```
  ! two connections answer to the database name "shop", so the second one is reported as "shop#2".
    They are separate databases — different host, port or user — and each is explained against itself.
```

Ничего при этом не теряется, но имя в сводке — то, которого вы не настраивали. Если это
мешает, дайте реплике собственное имя базы или читайте уведомление как то, чем оно и
является: как таблицу соответствия.

**У Eloquent второго этапа нет вовсе.** `QueryExecuted` не даёт доступа к соединению, на
котором можно выполнить `EXPLAIN` внутри той же транзакции. Первый этап работает
полностью на всех соединениях — при условии, что слушатель дотянулся до диспетчера, а не
до одного соединения, о чём сводка тоже скажет.

### Baseline при рефакторинге

Запись baseline ключуется как `правило|файл|фингерпринт`. Номера строки там намеренно нет,
поэтому обычные правки ничего не стоят — а вот **файл** есть, и фингерпринт — это
нормализованный SQL. Значит, записи двигают два вида рефакторинга:

- **переезд или переименование файла** — все записи, показывающие в него, перестают
  совпадать, и их находки возвращаются как новые;
- **изменение самого запроса** — новая колонка в `SELECT` даёт новый фингерпринт, хотя
  N+1 тот же самый.

Снаружи оба выглядят одинаково: находки появляются в коде, который вы вроде бы не трогали,
и столько же записей начинает сообщать, что они ничего не заглушили.

Лечится это одинаково и намеренно топорно — перегенерировать из полного прогона и
прочитать diff:

```bash
QUERY_GUARD_GENERATE_BASELINE=1 vendor/bin/phpunit
git diff --stat tests/query-guard-baseline.json
```

В diff записи должны **переезжать**: столько же ушло, столько же пришло, под новыми
ключами. Перегенерация, которая добавила больше, чем убрала, записала как существовавшее
что-то новое, а это единственное, чего baseline делать не должен, — разберитесь, что
появилось, до коммита.

Не правьте ключи руками вслед за переехавшим файлом. Ключ выводится, и написанный руками
чуть-чуть неверно он не глушит ничего, при этом выглядя как рабочий; удалять записи
руками можно — удаление способно сделать инструмент только строже.

### С dama/doctrine-test-bundle и транзакционными тестами

Настраивать нечего — и связку стоит назвать, потому что второй этап строился вокруг неё.
Этот бандл заворачивает каждый тест в транзакцию и откатывает её, поэтому созданные тестом
строки существуют на этом соединении и больше нигде. Отсюда и требование выполнять
`EXPLAIN` через то соединение, которое выполнило запрос, а не через новое: отдельное
соединение объяснило бы пустую базу и вернуло планы для данных, которых там нет.

Из этого следуют две вещи, которые полезно знать:

- **Соединение переиспользуется между тестами, трейс — нет.** Бандл держит одно соединение
  на весь сьют; query-guard открывает и закрывает трейс на каждый тест, поэтому находки
  остаются потестовыми в любом случае.
- **Планы кешируются на форму запроса и соединение, а не на тест.** Запрос, объяснённый в
  первом тесте, не объясняется заново в четырёхсотом — этим второй этап и остаётся
  подъёмным по цене, и это же значит, что план отражает данные такими, какими они были при
  первой встрече. На базе размером с фикстуры это было бы важно; второй этап и так не для
  таких баз, а `min-rows` — то, что заставляет его там молчать.

### Smoke-тесты производительности без query-guard

Нагрузочные smoke-тесты нужно гонять без расширения: middleware в DBAL и `EXPLAIN` второго этапа
на каждую форму запроса искажают ровно те замеры, ради которых тест существует, а `strict`
к тому же валит прогон по бюджету запросов, который тут и есть предмет измерения, а не баг.

Схема — группа и флаг. **Второй `phpunit.xml` не нужен**: ключ `--no-extensions` в PHPUnit
выключает на один прогон все зарегистрированные расширения, и синхронизировать копию
конфига не с чем.

**1. Вынесите smoke-тесты в свою группу:**

```php
use PHPUnit\Framework\Attributes\Group;

#[Group('smoke')]
final class AuctionBidLoadSmokeTest extends TestCase
```

**2. Исключите группу из обычных прогонов** — либо в конфиге, блоком `<groups>` верхнего
уровня (`<exclude>` внутри `<testsuite>` — это *путь*, а не группа):

```xml
<groups>
    <exclude>
        <group>smoke</group>
    </exclude>
</groups>
```

либо в командной строке: `vendor/bin/phpunit --exclude-group=smoke`. Оба варианта
оставляют `--group=smoke` рабочим: явная группа в командной строке перекрывает конфиг.

**3. Пропишите обе команды в composer:**

```json
{
    "scripts": {
        "test": "phpunit --exclude-group=smoke",
        "test:smoke": "phpunit --no-extensions --group=smoke"
    }
}
```

или в Makefile:

```make
test:
	vendor/bin/phpunit --exclude-group=smoke

test-smoke:
	vendor/bin/phpunit --no-extensions --group=smoke
```

`--no-extensions` выключает *все* расширения из `phpunit.xml`, а не только это. Если
smoke-набор зависит от другого расширения — вот тогда, и только тогда, нужен второй файл
конфигурации; и перенос каждого изменения `phpunit.xml` в него становится постоянной
обязанностью, а уехавший в сторону конфиг хуже, чем никакого.

Одна привычка держит в порядке остальное: smoke-набор гоняем строго последовательно.
Параллельные воркеры соревнуются друг с другом за CPU и базу, и замеры не стоят ничего.

## Требования

PHP 8.2+, PHPUnit 10.5 / 11 / 12 / 13.
Doctrine ORM 2 / 3 с DBAL 3 / 4 либо Laravel 11+.
Второй этап: MySQL 8 / MariaDB или PostgreSQL.

## Разработка

Локальный PHP не нужен, всё работает в контейнерах. `composer update`, а не `install`:
это библиотека, `composer.lock` намеренно не лежит в репозитории, и CI разрешает
зависимости заново на каждом прогоне.

```bash
docker run --rm -v "$PWD":/app -w /app -e COMPOSER_CACHE_DIR=/tmp/composer-cache composer:2 composer update
docker run --rm -v "$PWD":/app -w /app php:8.5-cli php vendor/bin/phpunit
docker run --rm -v "$PWD":/app -w /app php:8.5-cli php vendor/bin/phpstan analyse --memory-limit=1G
docker run --rm -v "$PWD":/app -w /app php:8.5-cli php vendor/bin/php-cs-fixer fix
```

Второй этап проверяется на синтетическом стенде со 100 000 строк:

```bash
docker compose -f tools/stand/docker-compose.yml up -d
tools/stand/capture.sh          # пересобрать эталонные планы в tests/Fixture/Explain
tools/stand/run-tier2-tests.sh  # прогнать ярус 2 против живых MySQL и PostgreSQL
docker compose -f tools/stand/docker-compose.yml down -v
```

В официальных образах `php` нет ни `pdo_mysql`, ни `pdo_pgsql`, поэтому
`run-tier2-tests.sh` при первом запуске собирает одноразовый образ на платформу.
Переменные `QG_MYSQL_IMAGE` / `QG_PG_IMAGE` позволяют подставить образы, которые в
проекте уже есть.

Ожидаемые флаги плана в этих тестах выставлены руками по прочитанному глазами выводу
`EXPLAIN`, а не сгенерированы нашим же парсером, иначе ошибка в понимании плана попала бы
разом и в код, и в его тест.
